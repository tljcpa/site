离线语音导航讲解机器人

实习

实习项目。在一台轮式讲解机器人本机上打通唤醒、离线中文识别、固定点位导航和到点讲解，并完成建图、导航延迟排查、v1.0 版本化发布与灾难恢复备份。最值得写的是一个自己引入的回压：导航桥常驻订阅障碍图，把障碍图拖慢了 20 到 42 秒。

时间
2026-08 ~ 2026-09
角色
需求拆解、方案与安全约束拍板、真机测试与验收（代码由 AI 编写执行）
成果
真机连续 5 次语音导航往返全部到达；定位并移除导航桥对障碍图的常驻订阅，障碍图时间差从落后 20–42 秒恢复到 0.32–0.35 秒
  • ROS 2 Humble
  • Python
  • sherpa-onnx
  • Piper TTS
  • PulseAudio
  • LiDAR SLAM
  • Docker
  • Bash

在某机器人公司实习期间做的项目。目标很具体：参观者说出「唤醒名 + 去某个地点」，机器人在本机完成收音、识别、匹配地点、下发导航、语音播报，到点后自动讲解。整条链路不依赖调试电脑，也不依赖外网。

机器人跑的是 Ubuntu 22.04 + ROS 2 Humble，导航和定位用厂商自带的栈，我的代码跑在一个 Docker 容器里。容器里没有 systemd，这一点后面会反复带来麻烦。

时间线

  • 08-27：启动，重建地图。
  • 09-02：本机离线版真机验收，连续 5 次语音导航往返全部 ARRIVED。
  • 09-03：v1.0 定版发布，带恢复脚本和校验。
  • 09-05 ~ 09-06：修网络，开发 v1.1（问答能力）。
  • 09-29：机器人收回前做最终全量备份。

语音链路

  • 识别：sherpa-onnx 中文 Zipformer CTC INT8 模型，单次推理 0.06–0.25 秒。真机验收时首次热身 0.292 秒，之后 0.075–0.142 秒。
  • 播报：本机 Piper TTS。在线 TTS 试过，会超时，所以固定用本地。
  • 收音：PulseAudio。旧方案 arecord plughw:2,0 在容器里用不了。
  • 唤醒：只处理带唤醒名的句子。也可以先只喊唤醒名，听到「我在，请说」后 15 秒内再说目标。

设计上有一条硬约束：目的地只能从固定点位表里选，不让大模型猜地点。「去」偶尔会被识别成「取」，但固定表匹配仍能解析出正确目标，这正是不用模型自由发挥的好处。

让机器人别乱动

一台会自己走的机器人，安全约束比功能更重要。

  • 导航桥没就绪、或已经有任务在跑时，拒绝下发新目标。
  • 旧代码里有个开关默认打开：精确说出点位名就跳过确认直接走。我把它改成默认关闭，并规定「嗯 / 好 / 是 / 可以」这类含糊回答不算确认。
  • 手柄的 2.4G 接收器丢了，临时做了一个网页遥控器。必须同时按住空格和方向键才会动；心跳超过 0.25 秒没收到就输出零速度；限速 0.08 m/s、0.20 rad/s。真机短距测试前进约 9.3 cm，退回原点误差约 1.2 cm。

建图

旧地图初始化会从 Initializing 掉进 Error，错误码 392（速度估计异常、特征点和匹配率不足）。我没有覆盖旧图，而是用新名字重建了一张 LiDAR 图。新图进入回环，末端偏差约 x −4.8 cm、y 2.8 cm、朝向 −4.9°，在约 0.15 m / 5° 的闭环门槛内；初始化后连续 7 次定位无错误。

拓扑图先做了 14 个节点、26 条有向边的 v1。后来导航在一些点位频繁报 NO_ASTAR_PATH，开阔区域也会原地转向不收敛。原地转向的根因我没有查清，初步怀疑在局部规划或底盘转向层。最后的处理是绕过去：新建 v2 拓扑，只保留开阔的目标点（8 个节点、14 条边），路线人工录制，删掉自动按 2 米连线产生的捷径。

最有价值的坑：自己把障碍图拖慢了 40 秒

现象：下发导航后，机器人有时几十秒甚至几分钟才动，日志里是 ObstacleMapTooOld。

根因：问题出在我自己写的导航桥。它为了做状态判断，常驻订阅了高度图和障碍图，QoS 设成了 RELIABLE + KEEP_LAST(10)。可靠传输下订阅者处理不过来，发布端就被拖住：障碍图的发布耗时从 0.3 ms 涨到 138.5–192.6 ms，超过了雷达约 100 ms 一帧的输入周期。积压越滚越大，障碍图最终落后真实时间 20–42 秒，导航栈判定数据过旧，拒绝规划。

解法：去掉常驻订阅后，障碍图时间差稳定在 0.32–0.35 秒。之后定了规矩：需要看这类大话题时，只允许短时采样，并且用 BEST_EFFORT + KEEP_LAST(1)。

教训是：在别人的系统上「只是旁听一下」也有代价。ROS 2 的可靠订阅会反向影响发布者。

其他坑

现象根因解法
重启后自动加载了旧图；v2 导航图报 Map not foundv2 保存时返回成功，但跨重启并没有持久化先加载 LiDAR v1，回到建图起点初始化，再用脚本把 v2 恢复到运行内存
启动脚本说「已经运行」，实际组件没起来只要总控进程在，旧脚本就直接返回，不查其余四个组件改成等五项全部就绪才返回，最长等 240 秒，并显示卡在哪一项
停在站点上重启后无法正常启动定位没恢复时，脚本按地图零点初始化先遥控回初始位置并对准，再启动
连上热点几秒就断，SSH 报 Broken pipe路由器中继失败，之后又发现默认网关指向一个不存在的地址停用失败的中继，写网络可携化脚本：中继失败或网段冲突就自动断开
「地」字读错多音字只在播报文本里替换成同音字，地点名不变

发布与备份

v1.0 打成一个应用层恢复包：压缩前约 937MB、压缩后约 725MB，含 3321 个文件和 33 个符号链接。发布前跑了 29 项语音逻辑测试和 36 项只读验收。

恢复脚本默认只做 --check 校验，加 --apply 才真正写入；写入前检查服务是否在运行，写入后逐文件 sha256 校验。只读检查已通过。

09-02 做了一套灾难恢复备份，4 个归档共约 9.15GiB，203 个条目全部哈希校验，并在空目录里实际解压过一遍。机器人收回前又做了一次全量备份，原始工作区约 22GB，按 FAT32 分卷保存。

诚实边界

  • v1.0 定版当天没有再下发移动任务。后加的三个站点还没逐点做往返验收，整机断电冷启动也没测过。
  • 恢复包只覆盖应用层，不是整机镜像。厂商系统、驱动和地图库不在里面。
  • 容器里没有 systemd，整机重启后要 SSH 进去手动启动一次。
  • 导航原地转向的根因没查清，是靠换开阔点位绕开的。
  • v1.1 的问答能力（中文 BM25 检索 + 大模型网关，各项单测通过）只在本地接假上游测过，没有部署到真机。
  • 有一次网络问题，我一度把「测试通过了」说成「我修好了」，实际是用户先手动断开了有线网才恢复的。这里如实记下，不算成果。
