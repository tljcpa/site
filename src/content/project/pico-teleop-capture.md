在某机器人公司实习期间做的，分两条线，底座都是开源的 [XRoboToolkit](https://github.com/XR-Robotics)。

- **遥操作采集**：操作员戴 PICO 4 Ultra 控制一台人形机器人的双臂、灵巧手和底盘，同时录 LeRobot 格式数据。
- **全景一键版**：在 XRoboToolkit 的 Unity 客户端上二次开发出一个独立 APK，把全景视角、录制和数采平台入口做成一键操作。

先说边界：软件链路都做通了，但**全景录制只到试采水平，真机上也没有形成成规模的数据集**。后面的数字都按这个口径来读。

## 一、遥操作与 LeRobot 采集

PICO 端直接用原版 XRoboToolkit APK，PC 端服务和视频推流也用开源组件。自己写的是中间那层 Python 包：遥操作逻辑、灵巧手映射、ROS 适配、安全层、视频桥和数据采集。

操作映射：

- 手柄位姿控制双臂末端，trigger 控制灵巧手开合。
- 左摇杆控制前后，右摇杆控制转向。
- 头部相机画面推回 PICO。
- `X` 开始录制，再按一次停止并保存 episode；`Y` 丢弃当前 episode；长按 `A` 双臂回初始位姿。

还做了一个单臂模式：只用右臂和右手 12 关节灵巧手，底盘强制禁用，左臂保持启动位姿不动。state 和 action 都是 19 维（7 维末端位姿 + 12 维手部命令）。双臂模式的 state 是 40 维，按 LeRobot v3.0 格式、10 fps 录制。

安全约定：

- grip 键是 deadman 开关，松手就不跟随。
- XR 输入超时，底盘停止，手臂保持当前目标。
- Ctrl-C 先保存正在录的 episode，再给底盘发零速、停控制器。
- 拿不到机器人当前位姿时，拒绝进入上肢跟随。

已知局限：灵巧手的 state 记录的是**发出去的目标命令**，不是实测手指位置。用这份数据训练时要注意这一点。

## 二、全景一键版 APK

原版 XRoboToolkit 的界面功能齐全，但现场操作员要点很多步。目标是做一个「戴上就能用」的版本，同时不破坏原有功能。

一开始想把两个 APK 嵌在一起，查下来不可行，APK 是独立应用。最后的做法是在原工程上覆盖一层新界面，原版完整界面保留为「高级模式」，用独立包名安装，不覆盖原版应用。

新增的部分：

- **本地全景**：用头部追踪在本机渲染全景，不依赖机器人回传画面。全景回正和录制起初绑在长按 B/Y，后来改成界面按钮，不占任何手柄键。
- **局域网节点发现**：UDP 广播发现主机，记住上次选择，但不自动连接。
- **数采平台面板**：公司已有的数采平台本身就能选机器人、启停采集、管理和导出数据，所以 APK 只做薄客户端，把平台嵌在一个可拖动、锁定在世界坐标的 WebView 面板里。
- **USB 直连**：企业版设备走 USB 网络共享。这个接口消费版账号解锁不了，所以又做了 ADB 端口转发作为回退。

主机端是一个 Python 服务：用 GStreamer 接入全景相机（默认 2880x1440@30 输入，归一化为 1280x640@30），录制会话输出 H.264 视频、frames/xr/robot 三份 parquet 和带 sha256 的 manifest，再提供一个导出成 LeRobot 目录结构的命令。

### 时钟同步

头显、主机、机器人三方的数据要对齐，靠一个 NTP 式的四时间戳交换：

```
offset = ((t2 − t1) + (t3 − t4)) / 2
```

RTT 扣掉设备端处理时间。保留最近 32 个样本，取 RTT 最低的 5 个，用它们 offset 的中位数。RTT 算出负数直接报错，不吞掉。

### 版本纪律

APK 从 0.2.0 一路迭代到 0.5.13，中间有一条 pilot 通道（0.3.3 到 0.3.43）和几版界面配色对照构建。规则只有一条：**versionName 和 versionCode 永不复用，打包脚本拒绝覆盖已有版本**。现场同时有好几台头显、好几个版本在测，这条规则省掉了很多「你装的到底是哪版」的来回。

## 工程坑

| 现象 | 根因 | 解法 |
|---|---|---|
| 新加的按钮看得见，射线点不了 | PICO 的射线交互只命中 UI 层（layer 5），代码动态创建的控件默认在 layer 0 | 动态控件继承父 Canvas 的 layer；节点列表不再每 0.5 秒重建，避免按下和抬起之间控件被换掉 |
| 视频连接偶尔被判成断线 | 只把 `TimedOut` 当超时 | `WouldBlock`、`TryAgain` 也按超时处理，空闲上限仍是 5 秒 |
| 主动停止录制却报「采集故障」 | GStreamer 拆管道时会抛 ERROR | 受控停止的状态优先于拆管道时的错误；端口探测加 `SO_REUSEADDR` 处理 `TIME_WAIT` |
| 数采面板上射线指针消失 | 面板是独立的合成层，盖住了 Unity 的射线 | 在面板内部同步绘制指针线，后来改成常显光标 |
| WebView 渲染异常、日志每帧刷屏 | elevation 设到 10000，导致系统按约 44320×42160 分配 surface | 放弃这种叠加方式，改用 composition layer 加可抓取交互 |
| 全景相机带宽只有 480 Mbit/s | 先以为是线的问题，实际是相机在 UVC 模式下自己声明为 USB 2.1 | 换线无用，这是设备限制，按这个带宽定分辨率 |
| 连上机器人 Wi-Fi 后开发机断网 | 系统把这个 Wi-Fi 设成了默认路由和 DNS | Wi-Fi 只走局域网，有线负责上网 |
| 一键安装把东西装进了 /root | 用户整段命令加了 sudo | 脚本禁止整段 sudo 运行，只在装依赖那一步请求权限 |

## 诚实边界

- **全景录制只能算试采**。一次 8 秒测试只存下 204 帧、约 6.6 秒视频，没有稳定 30 fps；那次 XR 位姿和机器人数据都是 0 行。本地留存的 3 个测试会话里，机器人数据也是空的。
- 全景相机接到人形机器人上的 USB 和带宽验证被推迟了，没有在机器人上部署过。
- 测试到 0.3.x 时，机器人端的追踪服务还连不上，当时记录的原话是「真实机器人遥操还不能虚报为完成」。之后是否打通，现有材料无法证实。
- 本地数据集是空的，真机实际采了多少条 episode 无法证实。
- 两条线都没有长时间连续运行的记录。测试版 APK 用的是 debug 签名。
- 改动没有整理成公开仓库，所以这页没有放代码链接。
