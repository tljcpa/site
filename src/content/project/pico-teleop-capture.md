这是我在某机器人公司实习时做的，目的很直接：给人形机器人的模仿学习攒训练数据。底座是开源的 [XRoboToolkit](https://github.com/XR-Robotics)，我在上面做了两件事。一是让操作员戴着 PICO 4 Ultra 控制机器人的双臂、灵巧手和底盘，同时录成 LeRobot 格式；二是在它的 Unity 客户端上改出一个独立 APK，把全景视角、录制和数采平台入口做成一键操作。软件链路都跑通了，但全景录制只到试采的程度，真机上也没有攒出成规模的数据集，下面的数字都只能按这个程度来看。

## 遥操作采集

PICO 端直接用原版 XRoboToolkit APK，PC 端服务和视频推流也是开源组件。自己写的是中间那层 Python 包，包括遥操作逻辑、灵巧手映射、ROS 适配、安全层、视频桥和数据采集。操作上，手柄位姿控制双臂末端，trigger 控制灵巧手开合，左摇杆管前后、右摇杆管转向，头部相机的画面推回 PICO。按 `X` 开始录制，再按一次停止并保存这条 episode；按 `Y` 丢掉当前这条；长按 `A` 双臂回到初始位姿。录坏了当场就能丢，这对后面的数据质量比事后清洗省事得多。

双臂模式的 state 是 40 维，按 LeRobot v3.0 格式、10 fps 录。我还做了一个单臂模式，只用右臂和右手 12 关节的灵巧手，底盘强制禁用，左臂停在启动位姿不动，state 和 action 都是 19 维（7 维末端位姿加 12 维手部命令）。

安全上有几条约定：grip 键当 deadman 开关，松手就不再跟随；XR 输入超时时底盘停下，手臂保持当前目标；Ctrl-C 先把正在录的 episode 存下来，再给底盘发零速、停控制器；拿不到机器人当前位姿就不进入上肢跟随。

有一个局限要提前说。灵巧手的 state 记的是发出去的目标命令，并不是实测的手指位置。用这份数据训练时，模型看到的手部"状态"其实是上一步的指令，手指没跟上或被挡住的情况它看不出来。

## 全景一键版 APK

原版 XRoboToolkit 功能很全，但现场操作员要点好多步才能开始采。我想要一个戴上就能用的版本，同时不丢原有功能。最开始想把两个 APK 嵌在一起，查下来不行，APK 是各自独立的应用。最后是在原项目上盖一层新界面，原来的完整界面留作高级模式，用独立包名安装，不会覆盖原版应用。

新加的东西里，本地全景是用头部追踪在本机渲染的，不依赖机器人回传画面。全景回正和录制起初绑在长按 B/Y 上，后来改成界面按钮，一个手柄键都不占。主机靠 UDP 广播在局域网里发现，会记住上次选的那台，但不自动连。公司已有的数采平台本身就能选机器人、启停采集、管理和导出数据，所以 APK 只做一个薄客户端，把平台塞进一个可拖动、锁定在世界坐标里的 WebView 面板。企业版设备走 USB 网络共享，这个接口消费版账号解锁不了，我又加了 ADB 端口转发作为备用。

主机端是一个 Python 服务，用 GStreamer 接全景相机，默认输入 2880x1440@30，统一缩到 1280x640@30。每次录制会话输出 H.264 视频、frames/xr/robot 三份 parquet 和带 sha256 的 manifest，另有一个命令把它导出成 LeRobot 的目录结构。

## 时钟同步

头显、主机、机器人三方的数据如果时间对不齐，图像和动作就会错位，模型学到的是错的对应关系。我用的是 NTP 式的四时间戳交换：

```
offset = ((t2 − t1) + (t3 − t4)) / 2
```

RTT 会扣掉设备端的处理时间。程序保留最近 32 个样本，取 RTT 最低的 5 个，用它们 offset 的中位数。RTT 算出负数就直接报错，不悄悄吞掉。

## 版本号

APK 从 0.2.0 一路迭代到 0.5.13，中间还有一条 pilot 通道（0.3.3 到 0.3.43）和几版界面配色的对照构建。我只定了一条规则，versionName 和 versionCode 永不复用，打包脚本也会拒绝覆盖已有版本。现场常常好几台头显装着不同版本同时在测，有了这条规则，就少了很多"你装的到底是哪版"的来回。

## 踩过的坑

| 现象 | 原因 | 处理 |
|---|---|---|
| 新加的按钮看得见，射线点不了 | PICO 的射线交互只命中 UI 层（layer 5），代码动态创建的控件默认在 layer 0 | 动态控件继承父 Canvas 的 layer；节点列表不再每 0.5 秒重建，避免按下和抬起之间控件被换掉 |
| 视频连接偶尔被判成断线 | 只把 `TimedOut` 当超时 | `WouldBlock`、`TryAgain` 也按超时处理，空闲上限仍是 5 秒 |
| 主动停止录制却报「采集故障」 | GStreamer 拆管道时会抛 ERROR | 受控停止的状态优先于拆管道时的错误；端口探测加 `SO_REUSEADDR` 处理 `TIME_WAIT` |
| 数采面板上射线指针消失 | 面板是独立的合成层，盖住了 Unity 的射线 | 在面板内部同步绘制指针线，后来改成常显光标 |
| WebView 渲染异常、日志每帧刷屏 | elevation 设到 10000，导致系统按约 44320×42160 分配 surface | 放弃这种叠加方式，改用 composition layer 加可抓取交互 |
| 全景相机带宽只有 480 Mbit/s | 先以为是线的问题，实际是相机在 UVC 模式下自己声明为 USB 2.1 | 换线无用，这是设备限制，按这个带宽定分辨率 |
| 连上机器人 Wi-Fi 后开发机断网 | 系统把这个 Wi-Fi 设成了默认路由和 DNS | Wi-Fi 只走局域网，有线负责上网 |
| 一键安装把东西装进了 /root | 用户整段命令加了 sudo | 脚本禁止整段 sudo 运行，只在装依赖那一步请求权限 |

## 还差什么

全景录制只能算试采。有一次 8 秒的测试只存下 204 帧、约 6.6 秒视频，没有稳定在 30 fps，那次的 XR 位姿和机器人数据都是 0 行；本地留着的 3 个测试会话里，机器人数据也是空的。全景相机接到人形机器人上的 USB 和带宽验证被推迟了，没在机器人上部署过。

测到 0.3.x 时，机器人端的追踪服务还连不上，我当时的记录原话是「真实机器人遥操还不能虚报为完成」，之后到底连没连上，现有材料证实不了。本地数据集是空的，真机实际采了多少条 episode 也证实不了。两条线都没有长时间连续运行的记录，测试版 APK 用的是 debug 签名。改动没有整理成公开仓库，所以这页没放代码链接。
